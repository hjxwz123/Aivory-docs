# Tools, MCP, and sandbox

Tools turn a model's reply into operations against external systems, the network, files, or a code execution environment. Administrators should treat them as a separate permission surface: the model being able to call tools does not mean every user, every model, and every workspace should have that capability.

Start with one low-risk, observable tool, and widen the scope only after you have confirmed call logs, cost, timeouts, and data boundaries. Tool enablement and a model's hosted-tool configuration are two layers of control: a tool existing doesn't mean every model will request it, and a model supporting native tools doesn't mean it is allowed to use every tool.

## Built-in tools and global disabling

The "Tools" page lists the available built-in tools and allows global disabling. Disabling is appropriate for security incidents, provider outages, cost anomalies, or maintenance windows; before restoring a tool, confirm its dependencies are available again.

Common built-in capabilities include web search, web scraping, Python execution, and image- or file-related operations. Whether a user can ultimately see or use one also depends on model capabilities, model tool policies, workspace permissions, and upstream service status.

Recommendations:

- On public demo sites, keep Python and high-cost tools off by default; provide only the necessary chat and web search capabilities first.
- In sensitive-data workspaces, avoid letting tools send unreviewed content to uncontrolled third-party services.
- After tool configuration changes, validate with a test account and minimal input; don't trial and error on real customer data first.

## Web search and scraping

Configure the search provider and API Key in "Tools", and—when needed—the self-hosted search address and search engine list. When web search is unconfigured or disabled, the tool should clearly return an unavailable state rather than fabricate search results.

Recommended rollout order:

1. Choose a search provider that meets your regional, privacy, quota, and latency requirements.
2. After saving the service address and key, test search results with a definite question.
3. Check that models are allowed to call web search, and set appropriate credits or quotas for user groups.
4. Watch external search cost, failure rate, and the risk of inappropriate content before deciding whether to open deep research or web scraping.

Treat search Keys as server-side secrets. Never put them in frontend variables or share them with regular users. On instances that can reach intranets, corporate networks, or restricted networks, also assess the SSRF and data-exfiltration risks of web scraping targets.

## MCP services

MCP services connect models to controlled external capabilities. Administrators add Streamable HTTP MCP addresses, required request headers, or credentials in "MCP services", and can test, sync, and enable/disable services.

Before adding an MCP service, answer four questions:

1. What external data can the service read or modify?
2. Are request headers, Bearer Keys, or OAuth credentials granted only the minimum necessary permission?
3. Which models, user groups, or workspaces should see these tools?
4. How do you degrade when the service is unavailable, tool output is abnormal, or high-frequency calls appear?

The recommended flow is to add one read-only, test MCP service first, run "Test" and "Sync", review the discovered method list and parameters, then enable it for a small number of administrators. Exposing production write-capable MCP services, personal access tokens, and admin keys to all chat models turns prompt injection or model mis-calls into external system risk.

Re-sync and re-test after every MCP server update, method change, or credential rotation. Before disabling or deleting an MCP service, check whether skills, prompts, workspaces, or user flows depend on it.

## Skills, prompts, and tool authorization

"Skills" and "Prompt library" provide reusable instructions, reference files, and behavior rules to models. They can enhance tool usage but never replace permission controls.

- Don't embed long-lived API Keys, database passwords, cookies, or one-time login links in skills.
- Document which tools a skill needs, what data scope it may access, and its safe behavior on failure.
- Before uploading skill assets, check copyright, privacy, and file types; administrator assets and user attachments differ in storage, backup, and access control.
- For every new skill, set up a repeatable test conversation and confirm the model doesn't call write-capable tools it shouldn't due to ambiguous instructions.

## Python sandbox availability

Python execution depends on a reachable sandbox service. The administrator tools page shows status based on the current effective configuration: with neither a local sidecar nor an external sandbox address, the page shows "Configure a sandbox first" and the Python interpreter switch stays off.

This notice applies to both the Personal edition and the Full edition: it reflects whether the current instance can safely reach a sandbox, not whether the user has administrator permission. Don't try to bypass it by force-enabling the interpreter.

### Three ways to run

| Option | Best for | Configuration points |
| --- | --- | --- |
| Full edition built-in sidecar | Standard Full edition | Compose already connects `http://sandbox:8000` on the internal network; no port needs to be exposed |
| Personal edition local profile | Trusted single machine | Set `SANDBOX_BASE_URL=http://sandbox:8000` and a matching key, then start with `--profile sandbox` |
| External sandbox | Isolation required or an existing execution platform | Fill in the HTTPS address and the same Bearer Key on the tools page or in the startup environment |

In all cases, the sandbox API must never be exposed to the public internet without authentication. The sandbox key is a Bearer credential; once leaked it could be used to create or access execution sessions.

## Security boundaries of the local sidecar

The official sidecar uses the host Docker socket to create a restricted container per session. It limits session-container CPU, memory, process count, a read-only root file system, temporary writable directories, upload size, idle reclamation, and execution duration as best it can, but the Docker socket itself still approximates high host privileges.

Therefore:

- Enable the local sidecar only on a fully controlled server; never place it on an untrusted shared host.
- Don't add `ports` to the `sandbox` service and don't expose it through a reverse proxy.
- Keep `SANDBOX_READ_ONLY_ROOTFS=1` unless you fully understand the disk and write risks of turning it off.
- Use `SANDBOX_MEMORY`, `SANDBOX_CPUS`, `SANDBOX_MAX_SESSIONS`, `SANDBOX_WORKSPACE_SIZE`, and execution-duration limits to leave headroom on the host.
- In public products, limit which users and which models may call Python; don't treat the container as an infinitely trusted arbitrary-code platform.

Both the Full edition and the Personal edition's optional profile start an image keep-alive service. It holds the sandbox runtime image so that, after an ops script prunes unreferenced images, the next Python call doesn't have to cold-pull a large image and fail on timeout. Don't casually delete this service as a redundant container.

## Persistent workspaces and files

Sandbox sessions usually maintain a workspace per conversation, reclaimable after idle. With local archiving or compatible object storage configured, a workspace can be restored after its session is reclaimed; local archiving suits a single node, while multiple application replicas should use shared object storage.

A persistent workspace does not mean every output is kept forever. Administrators should still define file retention, backup, deletion, and user data export policies, and make clear how conversation deletion, workspace deletion, and backup retention relate. Files containing confidential or personal data must not be synced automatically to uncontrolled object storage.

## Runtime and troubleshooting checks

When Python is unavailable, check in order:

1. Whether the tools page shows the sandbox as configured, and whether the address and key match.
2. Whether the `sandbox` container of the Full edition or the local profile is running and healthy.
3. Whether the host Docker daemon and Docker socket are available, and whether the runtime image has been pulled.
4. Whether sandbox resource limits, concurrent session caps, upload size, or execution timeouts are too low.
5. Whether the target model is restricted by globally disabled tools, model policies, or workspace permissions.

Don't fix errors by exposing the sandbox port, disabling authentication, or raising resource limits without bound. First read the redacted application and sandbox logs to determine whether the issue is network, authentication, image, resource, or model authorization.
