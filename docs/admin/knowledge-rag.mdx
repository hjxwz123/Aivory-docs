# Knowledge bases, RAG, and storage

A knowledge base lets the model retrieve document snippets within an access-restricted scope before answering. Reliable RAG is more than uploading files: it depends on working embeddings, correct dimensions, successful parsing and indexing, appropriate storage boundaries, and access control for users and workspaces.

## Workflow and acceptance checkpoints

A typical flow:

1. A user uploads a file, or an administrator creates a knowledge base resource.
2. The system validates size and type, and stores the original object.
3. The parser extracts text, tables, or image-related content.
4. The text is chunked, and the embedding model generates vectors.
5. Vectors and document metadata are written to the vector backend of the current deployment.
6. When a user asks a question, the system retrieves only from scopes the user has permission to access and provides relevant snippets to the model as context.

Upload completion does not mean the document is already searchable. Wait until the document status shows completed, then run a retrieval test with a sentence you can verify exactly in the file. On failure, keep the original file, check the task errors and model/service logs, and don't repeatedly re-upload the same file to mask the root cause.

## Embedding models and dimensions

Add a real embedding model under channels and models, or set a deployment-level embedding fallback. Without an external embedding model, the system can fall back to a basic local embedding; that is fine for trials, but it should not be the long-term baseline for high-quality semantic retrieval.

The most important constraint is dimension consistency: `EMBEDDING_DIM`, the dimension in the model settings, and the model's real output must be identical. A dimension mismatch causes indexing failures, empty retrieval results, or the isolation of incompatible vectors.

When changing the embedding model, vendor, or dimension, follow this process:

1. Record the old model, the old dimension, and the business scope of the current knowledge bases.
2. Add the new embedding model and validate it with a small sample document.
3. Update the relevant model or deployment settings.
4. Trigger a vector rebuild of the affected knowledge bases in the admin backend.
5. Run retrieval acceptance on both old content and newly uploaded content, and only retire the old model after confirming all indexes have finished building.

Never delete the only copy of the original files or backups during a rebuild. Vectors can be rebuilt; original documents and metadata usually cannot be recovered accurately once lost.

## Vector backends: Personal edition and Full edition

| Deployment | Where vectors live | Operational impact |
| --- | --- | --- |
| Personal edition | Embedded vectors in the SQLite database | `aivory.db` and files are under `DATA_DIR`; single instance, must not live on a network file system |
| Full edition | Qdrant data volume | Protect Qdrant together with PostgreSQL and files as one consistent backup unit |

The Personal edition already has vector retrieval; you don't need to deploy Qdrant separately for RAG. The Full edition uses its internal Qdrant by default; unless you have a deliberate external-service design, don't expose its port or let the application connect to an uncontrolled instance.

`VECTOR_BACKEND` is deployment-level topology configuration. The official Personal edition is fixed to SQLite vectors, and the official Full edition is fixed to Qdrant; change it only for custom deployments and only if you understand the consequences. See [Environment variables](../deployment/environment.mdx).

## Document parsing and OCR

Plain text, Office files, spreadsheets, and PDFs with a text layer can be handled by the local parsing pipeline. Scanned documents, image-only PDFs, complex layouts, or high-quality OCR scenarios usually require an external parsing service such as MinerU.

When configuring MinerU, fill in an API address and key reachable from the application, and first validate with one non-sensitive scanned PDF. Without configuration, don't expect images and scanned documents to automatically produce high-quality text; the system may store only placeholder content or limited extraction results.

Troubleshooting order for parsing failures:

1. Confirm the file isn't corrupted, doesn't exceed the upload limit, and isn't password-protected or an unreadable format.
2. Check network, authentication, quota, and timeouts of the corresponding parsing service.
3. Confirm the object storage address is reachable by the parsing service; some external parsing flows require downloadable object URLs.
4. Review document task errors, application logs, and provider responses to determine whether parsing, embedding, or the vector write failed.

Never expose private buckets, internal file servers, or databases to the public internet just to make OCR succeed.

## Storage and upload policies

The "Storage & uploads" page manages where application objects are kept, upload limits, and retention boundaries. Local storage by default suits single machines: objects such as avatars are written to a local object directory, and user uploads and artifacts live under the application data directory. It is simple and easy to back up, but not suitable for multiple application replicas sharing it at the same time.

When you need multiple replicas, cross-node access, or collaboration with external parsing services, use controlled object storage and follow least privilege:

- Use a separate bucket/prefix and don't share administrator credentials with other business systems.
- Grant only the necessary read, write, list, or presign permissions; avoid an account-wide admin key.
- Define lifecycle, versioning, encryption, region, and access-log policies.
- Treat object storage credentials and configuration as sensitive; backend configuration exports may include them.
- Test upload, download, thumbnails, parsing, share snapshots, and deletion before migrating real user files.

Upload caps, single-file size limits, total quotas, and administrator icon/skill asset limits jointly shape the user experience. Before raising limits, also assess the reverse proxy's request body cap, disk/object-storage cost, parsing memory, and backup size.

## Permissions, workspaces, and sharing

A knowledge base is not a globally public search. Administrators should combine users, user groups, and workspaces to check who can upload, view, retrieve, edit, or delete documents.

- Put different customers, teams, or data classifications in different knowledge bases and workspaces.
- Use read-only sharing by default; grant edit or upload permissions only to people genuinely responsible for maintaining the material.
- Before sharing a conversation, check whether referenced snippets, attachments, preview images, and tool artifacts will be pulled into the read-only snapshot.
- After user deletion, workspace removal, or permission changes, verify that old sessions and old knowledge bases no longer expose content they shouldn't.

The admin-side "Documents & knowledge", "Content resources", and "Files" pages are good for checking status, cleaning up orphaned resources, and handling user feedback. Confirm backup and retention policies before deleting, because the deletion scope of vectors, original files, and artifacts is not always identical.

## Backup and recovery

Backups must cover relational data, vectors, and original files together. For the Personal edition, focus on the whole `DATA_DIR`; for the Full edition, focus on the consistency of PostgreSQL, Qdrant, Redis, the sandbox archive volume, and `DATA_DIR`.

The full backend backup can be used for migration and recovery, but before restoring, stop writes, save a copy of the current data, and validate in an isolated environment. After recovery, check administrator configuration, attachments, knowledge base states, vector retrieval, and object storage access. For the detailed process, see [Upgrades, backup, and recovery](../deployment/upgrade-backup.mdx).
