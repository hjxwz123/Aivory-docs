# Channels, models, and policies

A channel stores "how to connect to an upstream provider"; a model stores "which specific model can be called through that connection". Managing them separately lets the same model ID coexist across different accounts, regions, gateways, or cost policies.

The minimum conditions for users to chat normally: there is an enabled, usable channel; at least one enabled chat model is linked to that channel; and a valid default chat model is selected in the model policies. For the complete first-run flow, see [Administrator first-run setup](./first-run.mdx).

## Planning channels

Create channels around credentials and failure boundaries rather than stuffing every provider into one connection.

| Scenario | Recommendation |
| --- | --- |
| The same provider has production and test Keys | Create two channels with names that clearly mark the environment; never let a test Key become the default model |
| The same model is available through two gateways | Create two channels and two model records for independent ordering, disabling, or fallback |
| Traffic must be split by team, region, or cost | Use a separate channel for each contract, region, or budget pool |
| The provider has no model-list endpoint | Keep the channel and add models manually; list import is not a prerequisite for using a channel |

API Keys in channels should only be saved through the admin backend. Never write provider Keys into `VITE_*`, frontend pages, public examples, browser request parameters, or application logs. When rotating a key, first create or update a controlled channel and verify with a real model request, then disable the old credential; don't delete it outright and break user conversations.

## Adding and verifying channels

When creating a channel in "AI & models → Channels", fill in the name, provider type or API format, Base URL, API Key, and enabled state.

1. Choose the API format based on the provider's protocol. The same model name does not imply API compatibility.
2. Fill in the complete Base URL. OpenAI-compatible gateways usually end with `/v1`, but don't apply that rule to every provider automatically.
3. Enable the channel only after you have confirmed the credentials are correct.
4. Right after saving, add one test chat model and send a short request to verify network, authentication, model authorization, and quota.

Common mistakes include: a Base URL missing the version path, entering the web console address instead of the API address, a proxy rewriting requests to the wrong path, a Key without permission for the target model, a provider that only allows IPs from specific regions, or insufficient account balance. When a model call fails, check the channel and the upstream response first; don't start by changing the default policy.

## Automatic import and manual model creation

There are two ways to add models:

- **Auto-add models supported by the channel**: request the model list from the channel and import whatever is discoverable. Best for OpenAI-compatible providers that allow model listing.
- **Manual creation**: fill in the provider's real request ID, display name, capability type, and associated channel. Best for providers that don't open the model list, private gateways, or inference-only Keys.

After an import you still need to check every record: whether it should be visible to users, whether it is enabled, which capability it is—chat/embedding/image/audio—whether the request ID matches the provider documentation, and whether cost, context, and multimodal capabilities are described correctly. Automatic import does not replace these operational judgments.

Different channels can have exactly the same model ID. For example, when channel A and channel B both support `gpt-5`, each can have its own `gpt-5` record. They don't overwrite each other, because the runtime uses the model record together with its associated channel to decide how to send the request.

Disabling a channel makes its models unavailable for new requests; disabling or deleting a model affects default policies, fallback policies, user pickers, and ongoing operational flows. Before a production change, check whether the model is referenced by the default model, task models, workspace policies, plans, or user favorites.

## Model types and capabilities

A model should only be assigned roles it actually supports:

| Type | Purpose | Configuration focus |
| --- | --- | --- |
| Chat model | Ordinary conversations, tool calling, tasks, and fallback | Request ID, context, output limit, vision and tool capabilities |
| Embedding model | Vector generation after knowledge base chunking | Output dimension must match `EMBEDDING_DIM` and the index |
| Image model | Image generation or editing | Capabilities, sizes, cost, file retention policy |
| Audio model | Speech recognition or related input capabilities | Upstream format, file size, duration, and quota |

Don't mark an arbitrary chat model as an embedding model, and don't assume every model from the same provider supports images, tools, JSON, or streaming. Wrong capability flags usually show up as "the model appears in the picker, but the very first request fails".

## Model policies

Maintain system-level selection rules in "Settings → Model policies".

- **Default chat model**: the main model for new conversations, and the only hard prerequisite for a first chat.
- **Task model**: used by background or auxiliary tasks. Recommended, but ordinary chat works without it.
- **Tool-routing model**: can help automatic tool mode decide when to call tools; when left empty, the regular policy applies.
- **Verification model**: used for answer review or validation. It adds cost and latency; choose a stable model suited to verification tasks.
- **Fallback model**: the degraded choice when the primary model's first-token wait exceeds the threshold or it is unavailable. The fallback model must be verified independently, and its capabilities, privacy level, and cost must match what you promise.

Right after setting the default model, start one ordinary text conversation; after setting a fallback, simulate an unavailable primary channel during a controlled window to verify the degradation. Never make an unverified cheap model the global fallback outright.

## Ordering, labels, visibility, and quotas

Model ordering and labels affect discoverability in the user picker, and are a good way to make operational semantics such as "Recommended", "Economy", "Long context", and "Image" explicit. For different user groups, plans, or workspaces, you need user groups, credits, model quotas, and permission policies to restrict which models are visible and how much can be consumed.

Start from "users see only a few verified models by default". As demand grows, add categories by cost, context, speed, or data-processing boundaries; don't expose every model a provider allows importing by default.

## Provider-hosted tools

Aivory never configures provider-hosted tools automatically for OpenAI or other channels' models. All models ship without such tools by default. If a provider genuinely supports them and you explicitly want users to be able to call them, add a compatible tool request configuration in that model's tool settings.

Treat this configuration as its own security assessment: clarify which users see it, what data is sent to the provider, how fees are accounted for, the degradation path on failure, and whether provider tools duplicate or conflict in permission terms with Aivory's built-in web search, Python, and MCP.

## Changes and troubleshooting

A safe channel/model change process:

1. Record the current default model, fallback model, plans referencing the model, and quotas.
2. Create or modify the channel and save the new credentials.
3. Send a short request with the target model and check real capabilities such as streaming responses, tools, images, or embeddings.
4. Only then change model enabled states, ordering, and global policies.
5. Watch usage, error records, and user feedback before disabling the old channel or old model.

If "Auto-import" fails, first check whether the provider allows listing models; if "the model exists but chat fails", check the model type, model request ID, channel enabled state, and default policy; if "the wrong upstream is picked for the same ID", check the channel associated with the model record, not just the display name.
