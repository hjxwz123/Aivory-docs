# Users, Sign-in, and Workspaces

Access control determines who can enter the instance, how they sign in, which workspaces and resources they can see, and how administrators handle accounts when things go wrong. Establish a recoverable administrator sign-in path first, then tighten sign-up and sign-in policies; never close your only available entry point before verifying OAuth or the administrator password.

## User lifecycle

The "Users" page supports viewing, creating, and maintaining accounts, and lets you drill into a user's conversations, knowledge bases, memories, sign-in history, and usage. Follow the principle of least impact for administrative actions:

- **Create/modify accounts**: Confirm email ownership, display name, role, and initial password. Never send plaintext passwords through chat, screenshots, or tickets.
- **Promote to administrator**: Grant the role only to trusted personnel. Administrators can read operational data, modify channels, export configuration, and affect user access.
- **Suspend or ban**: Appropriate for security incidents, abuse, or employee departures. First record the reason, time, and responsible person, and verify that the user's existing sessions are correctly terminated.
- **Reset passwords or disable 2FA**: Verify identity first, then notify the account owner after the action and record audit information.
- **Delete users**: A data-affecting action. First confirm legal retention requirements, workspace ownership, shared materials, and the backup strategy; do not treat deletion as "temporary disabling".

Regularly review sign-in history, unusual regions/IPs, failed sign-ins, and high-frequency sign-ups. Don't rely on a single metric to judge an attack; evaluate email, behavior, usage, and user feedback together.

## Sign-up and password sign-in

The "Sign-up policy" section controls whether sign-up is open, per-IP sign-up limits, sign-up/sign-in captcha, email verification, allowed email domains, password sign-in, and how the entry point is presented.

Recommended baseline for public deployments:

1. Initially disable open sign-up or enforce a strict email domain allowlist.
2. When open sign-up is required, enable captcha, email verification, and reasonable per-IP limits.
3. Keep at least one verified password or identity-provider sign-in path for administrators.
4. Before a real release, run through sign-up, verification, sign-in, sign-out, token refresh, password reset, and the behavior after being disabled with a non-administrator test account.

Password sign-in can coexist with OAuth. If you disable password sign-in, switch to an identity-provider selector, or enable auto-redirect, the system requires at least one enabled sign-in identity provider; auto-redirect also requires selecting a default provider. Test in a different browser or an incognito window before closing the original entry point so you don't lock every administrator out.

## OAuth, OIDC, and account linking

The "Sign-in identity providers" section supports GitHub, Google, Apple, standard OAuth2, and OIDC. Each identity provider should use its own controlled Client ID, Client Secret, and exact callback URL.

Steps to securely roll out an identity provider:

1. Complete public HTTPS domain and reverse proxy configuration first.
2. Create the identity provider in the admin console and copy the callback URL shown there into the provider's console.
3. Start a sign-in with a test account and verify new-user creation, sign-in for existing accounts, and explicit account linking.
4. Check that email matching, automatic account creation, the initial password policy, and user group assignment behave as expected.
5. Only then expose the entry point to real users or enable auto-redirect.

Before enabling automatic account creation, evaluate whether your organization allows any user who satisfies the identity provider's conditions to enter. If you use multiple public domains, configure a fixed OAuth callback domain and allowed return URLs; see [Domains, HTTPS, and OAuth](../deployment/domain-tls-oauth.mdx).

When third-party sign-in reports `token_exchange_failed`, a healthy account link does not mean the server's outbound network is healthy. Check the HTTPS path from the server to the provider's token endpoint, DNS, proxies, firewalls, callback URLs, and system time, rather than repeatedly unlinking user accounts.

## Two-factor authentication and session security

Users can enable two-factor authentication, and administrators can help disable it after identity verification. Two-factor authentication is not a substitute for:

- strong, unique administrator passwords;
- protecting `JWT_SECRET`, database passwords, and OAuth Client Secrets;
- HTTPS, correct cookie/reverse-proxy configuration, and timely updates;
- prompt banning and session revocation for stolen devices or departed staff.

Sessions use short-lived access tokens and long-lived refresh tokens. Shortening the access-token lifetime reduces the window in which a leaked token is useful; the refresh-token lifetime should balance user convenience against device risk. A complete multi-device policy should combine server-side session records, device binding, refresh-token rotation, anomalous refresh detection, session revocation after password changes, and administrator bans, rather than just shortening one TTL.

## User groups, plans, and workspaces

User groups map a set of accounts to model visibility, quotas, credits, plans, or operational rules. Define a small number of clear groups—administrators, internal staff, trial, paid, and restricted users—instead of exception combinations that are hard to track.

Workspaces are for team collaboration. When creating workspaces and managing members, confirm:

- who the workspace owner is and how ownership transfers after a member leaves or is deleted.
- whether members can create, edit, and delete conversations, projects, knowledge bases, and files.
- whether invite links have a reasonable validity period, allow external email addresses, and should be revoked after use.
- keeping data for different customers, legal entities, or confidentiality levels in separate workspaces; don't rely on verbal agreements for isolation.

After changing roles, user groups, or workspace membership, verify with a low-privilege test account that access is actually tightened or opened. Don't judge permissions from the administrator view alone.

## Security operations checklist

- Keep at least two independent, recoverable administrator sign-in paths, and store the recovery procedure safely.
- Rotate OAuth, SMTP, model channel, and storage keys regularly; after rotation, run real sign-in and send tests.
- Before enabling open sign-up or automatic account creation, define the allowed user scope, email domains, and abuse-handling mechanism.
- Include users, workspaces, sign-in history, and sensitive administrator actions in periodic reviews.
- Before deleting, banning, exporting, or restoring data, record the operator, reason, scope, and rollback plan.
