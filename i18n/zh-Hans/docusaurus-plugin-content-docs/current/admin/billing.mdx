# 套餐、积分与支付

套餐、积分和支付把模型成本、用户可用能力与订单流程连接起来。建议先用管理员和测试账号验证配额与积分，再开放真实支付；支付渠道、回调密钥和配置导出都应按高敏感资产管理。

## 先建立成本边界

在添加商品前，先明确每一类用户可以消耗什么：

- 可以使用哪些聊天、图片、语音或 embedding 模型。
- 每日消息、图片、上传、工具调用和并发生成的合理上限。
- 积分如何换算到不同模型与服务商成本，免费额度是否足够用于试用。
- 超出额度后是拒绝、提示充值、切换低成本模型，还是由管理员手工处理。

先用低成本模型和小额度测试。不要在没有成本监控、滥用限制和退款/人工处理流程时公开高价模型、深度研究、图片生成或 Python 执行。

## 用户组、套餐与模型配额

“套餐”中的用户组可用于为一组用户分配默认能力与经营规则；“积分与配额”用于设置积分套餐、模型额度和相关策略。

推荐从简单分层开始，例如：管理员、内部成员、试用用户和付费用户。对每一层明确默认模型、可见模型、每天配额、积分余额上限和敏感工具权限。避免为单个用户建立大量不可追踪的例外；特殊情况优先使用一次性积分调整或有限期兑换码，并记录原因。

调整模型配额前应检查模型实际价格、上下文长度、输出上限和工具成本。配额变化通常只影响后续请求，不会自动抹去已有使用记录或已创建订单。

## 积分套餐与兑换码

积分套餐定义用户可以购买或获得的积分产品。创建前确认名称、展示文案、价格、赠送积分、启用状态、排序以及适用的支付方式。上线时先创建一个隐藏或测试用套餐，完成购买、支付回调、积分入账、取消和重复回调测试后再公开。

兑换码适合邀请、补偿、企业发放和营销活动。管理时应明确：

- 单码或批次的积分值、有效期、使用次数和适用用户范围。
- 是否允许同一用户多次兑换，错误输入和高频尝试如何限流。
- 码一旦泄露是否能撤销，批次删除是否会影响已经入账的积分。
- 兑换记录、批次负责人和活动结束后的清理策略。

不要把兑换码列表直接放到公开页面、客户端常量或客服截图中。生成大批量兑换码后先导出到受控的加密存储，再通过能撤销或追踪的渠道发放。

## 支付渠道与支付方式

支付渠道保存某个支付服务商的连接和 webhook 配置；支付方式决定用户在结算页可选择的具体方式。渠道和方法分开，可以让同一渠道提供多个方式，也能在故障时独立停用一种方式。

安全上线流程：

1. 在支付服务商创建受限 API/Webhook 凭据，区分测试与生产环境。
2. 在后台创建支付渠道，使用后台显示的 webhook 地址注册回调。
3. 校验 webhook 签名或密钥，确保回调通过 HTTPS 到达公开实例。
4. 创建一个仅管理员可见的测试支付方式和测试积分套餐。
5. 用真实服务商测试环境完成下单、成功、失败、取消、重复回调和延迟回调。
6. 检查订单状态、积分入账、用量、退款或人工对账流程，再切换生产环境并公开。

测试环境与生产环境必须使用不同密钥和不同商品配置。不要将测试渠道误设为对普通用户开放，也不要把生产 webhook 密钥提交进版本控制或配置截图。

## 订单与对账

“支付订单”页面用于查看订单状态、过滤异常、在必要时人工对账或清理测试订单。人工操作应只修复已核实的外部支付事实，不能作为绕过支付验证的常规发积分方式。

发生争议、回调失败或金额不一致时：

1. 保留支付服务商的订单号、事件 ID、时间、金额、币种和签名验证结果。
2. 检查 Aivory 订单状态、是否已入账、是否收到重复 webhook。
3. 先在支付服务商后台确认最终状态，再执行人工对账。
4. 记录操作者、原因和关联证据，避免多个管理员重复发放积分。

支付 webhook 的网络入口需要 HTTPS、稳定的公网回调地址和合理限流。不要依赖浏览器打开后台页面来“触发”入账。

## 运营与审计

用量、分析、订单、兑换记录和用户反馈应一起看：积分余额增长不一定代表真实模型成本可控，模型高峰与异常工具调用也可能造成成本风险。

上线后定期检查：

- 每个用户组的平均成本、失败率、退款和可疑高频使用。
- 订单与支付服务商账单是否一致，是否存在长期挂起或重复订单。
- 模型价格、积分换算、免费额度是否仍然覆盖成本。
- 管理员是否仍能访问并轮换支付渠道密钥，Webhook 是否能继续验证。

支付、渠道、OAuth、SMTP 和存储配置包含机密。管理员配置导出与完整备份都应加密保存、限制访问，并按处理生产密钥的同等标准保护。
