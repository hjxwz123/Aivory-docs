# Plans, Credits, and Payments

Plans, credits, and payments connect model costs, what users are able to do, and the order flow. Validate quotas and credits with an administrator and test accounts before enabling real payments; treat payment channels, callback secrets, and configuration exports as highly sensitive assets.

## Establish cost boundaries first

Before adding products, define what each class of user can consume:

- which chat, image, speech, or embedding models they may use.
- reasonable daily limits on messages, images, uploads, tool calls, and concurrent generations.
- how credits convert to the costs of different models and providers, and whether the free allowance is enough for trials.
- what happens after limits are exceeded: reject, prompt to top up, fall back to low-cost models, or handle manually by administrators.

Test first with low-cost models and small allowances. Don't publicly expose expensive models, deep research, image generation, or Python execution without cost monitoring, abuse limits, and refund/manual-handling workflows.

## User groups, plans, and model quotas

User groups in "Plans" can assign default capabilities and business rules to a group of users; "Credits and Quotas" sets credit packages, model quotas, and related policies.

Start with simple tiers, for example administrators, internal members, trial users, and paid users. For each tier, define the default model, visible models, daily quota, credit balance cap, and permissions for sensitive tools. Avoid building large numbers of untraceable exceptions for individual users; for special cases, prefer one-off credit adjustments or limited-time redemption codes, and record the reason.

Before adjusting model quotas, check the model's actual price, context length, output limit, and tool costs. Quota changes typically only affect subsequent requests; they do not retroactively erase existing usage records or already-created orders.

## Credit packages and redemption codes

Credit packages define the credit products users can purchase or receive. Before creating one, confirm the name, display copy, price, bonus credits, enabled state, ordering, and applicable payment methods. When launching, first create a hidden or test package, and only publish it after completing purchase, payment callback, credit crediting, cancellation, and duplicate-callback tests.

Redemption codes suit invitations, compensation, enterprise distribution, and marketing campaigns. When managing them, define:

- the credit value, validity period, usage count, and applicable user scope for a single code or batch.
- whether the same user may redeem multiple times, and how mistyped input and high-frequency attempts are rate-limited.
- whether a leaked code can be revoked, and whether deleting a batch affects credits that were already credited.
- redemption records, batch owners, and the cleanup strategy after a campaign ends.

Don't put redemption code lists directly on public pages, client-side constants, or support screenshots. After generating a large batch, export it to controlled encrypted storage first, then distribute it through channels that can revoke or track it.

## Payment channels and payment methods

A payment channel stores the connection and webhook configuration for one payment provider; payment methods determine which specific options users can choose at checkout. Keeping channels and methods separate lets one channel offer multiple methods and allows disabling a single method independently during an outage.

Secure rollout process:

1. Create restricted API/webhook credentials with the payment provider, separating test and production environments.
2. Create the payment channel in the admin console and register callbacks using the webhook URL shown there.
3. Verify webhook signatures or secrets, and confirm callbacks reach the public instance over HTTPS.
4. Create a test payment method and test credit package visible only to administrators.
5. Complete order placement, success, failure, cancellation, duplicate callbacks, and delayed callbacks using the provider's real test environment.
6. Review order status, credit crediting, usage, refunds, or manual reconciliation, then switch to the production environment and publish.

Test and production environments must use different keys and different product configurations. Never leave a test channel open to regular users, and never commit production webhook keys to version control or configuration screenshots.

## Orders and reconciliation

The "Payment orders" page is for viewing order status, filtering anomalies, and, when necessary, reconciling manually or cleaning up test orders. Manual actions should only fix verified external payment facts; they must not become a routine way to hand out credits that bypasses payment verification.

When disputes, callback failures, or amount mismatches occur:

1. Preserve the payment provider's order number, event ID, timestamp, amount, currency, and signature verification result.
2. Check the Aivory order status, whether credits were already credited, and whether duplicate webhooks were received.
3. Confirm the final status in the payment provider's console first, then perform manual reconciliation.
4. Record the operator, reason, and linked evidence to prevent multiple administrators from crediting the same order twice.

The network entry point for payment webhooks requires HTTPS, a stable public callback address, and reasonable rate limiting. Don't rely on opening an admin page in a browser to "trigger" crediting.

## Operations and audit

Usage, analytics, orders, redemption records, and user feedback should be reviewed together: growing credit balances don't necessarily mean real model costs are under control, and model peaks plus abnormal tool calls can also create cost risk.

Check regularly after launch:

- average cost, failure rate, refunds, and suspicious high-frequency usage per user group.
- whether orders match the payment provider's bills, and whether there are long-pending or duplicate orders.
- whether model prices, credit conversion, and free allowances still cover costs.
- whether administrators can still access and rotate payment channel keys and whether webhooks still verify.

Payment, channel, OAuth, SMTP, and storage configurations contain secrets. Administrator configuration exports and full backups should all be encrypted at rest, access-restricted, and protected to the same standard as production keys.
