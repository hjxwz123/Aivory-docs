# 工具、MCP 与沙盒

工具会把模型回复变成对外部系统、网络、文件或代码执行环境的操作。管理员应把它们视为独立的权限面：模型能调用工具，不等于所有用户、所有模型、所有工作区都应获得该能力。

建议从一个低风险、可观察的工具开始，确认调用日志、成本、超时和数据边界后再扩大范围。工具启用与模型的托管工具配置是两层控制：一个工具已存在，不代表每个模型都会请求它；一个模型支持原生工具，也不代表它被允许使用所有工具。

## 内置工具与全局禁用

“工具”页面列出可用的内置工具，并允许全局禁用。禁用适合处理安全事件、服务商故障、成本异常或维护窗口；恢复前应确认依赖服务已经可用。

常见内置能力包括网页搜索、网页抓取、Python 执行、图像或文件相关操作。用户是否能最终看到或使用它，还取决于模型能力、模型工具策略、工作区权限和上游服务状态。

建议：

- 对公开演示站，默认关闭 Python 和高成本工具，先提供必要的聊天与搜索能力。
- 对敏感数据工作区，避免让工具把未审查内容发送到不受控的第三方服务。
- 工具配置变更后，使用测试账号和最小输入验证，不要先在真实客户数据上试错。

## 网页搜索与抓取

在“工具”中配置搜索服务商、API Key，或需要时配置自托管搜索地址与搜索引擎列表。搜索未配置或被禁用时，工具应明确返回不可用状态，而不会伪造搜索结果。

推荐的上线顺序：

1. 选择能满足地区、隐私、额度和延迟要求的搜索提供方。
2. 保存服务地址与密钥后，用一个确定的问题测试搜索结果。
3. 检查模型是否被允许调用搜索，并为用户群设置合适的积分或配额。
4. 观察外部搜索的费用、失败率和不当内容风险，再决定是否开放深度研究或网页抓取。

搜索 Key 需要视作服务端机密。不要把它放入前端变量或分享给普通用户。对于可访问内网、企业网或受限网络的实例，还要评估网页抓取目标的 SSRF 与数据外泄风险。

## MCP 服务

MCP 服务用于把模型连接到受控的外部能力。管理员在“MCP 服务”中添加 Streamable HTTP MCP 地址、必要请求头或认证信息，并可以测试、同步和启用/停用服务。

添加 MCP 前先回答四个问题：

1. 该服务可读取或修改哪些外部数据？
2. 请求头、Bearer Key 或 OAuth 凭据是否只授予最小权限？
3. 哪些模型、用户组或工作区应当看到这些工具？
4. 服务不可用、工具输出异常或出现高频调用时如何降级？

推荐流程是先添加一个只读、测试用的 MCP 服务，执行“测试”和“同步”，检查发现的方法列表及参数，再启用给少量管理员。将生产写入型 MCP、个人访问令牌和管理密钥直接公开给所有聊天模型，会把提示注入或模型误调用变成外部系统风险。

每次 MCP 服务器更新、方法变化或凭据轮换后都应重新同步和测试。禁用或删除 MCP 前，先检查是否被技能、提示词、工作区或用户流程依赖。

## 技能、提示词与工具授权

“技能”和“提示词库”用于把可复用的指令、参考文件和行为规则提供给模型。它们可以增强工具使用，但不能替代权限控制。

- 技能中不要写入长期 API Key、数据库密码、Cookie 或一次性登录链接。
- 说明一个技能需要哪些工具、可访问的数据范围和失败时的安全行为。
- 上传技能资产前检查版权、隐私和文件类型；管理员资产与用户附件的保存、备份和访问控制不同。
- 对每个新技能建立可重复的测试对话，检查模型不会因模糊指令调用不该调用的写入型工具。

## Python 沙盒可用性

Python 执行依赖可访问的沙盒服务。管理员工具页会根据当前有效配置显示状态：如果既没有本地 sidecar，也没有外部沙盒地址，页面会显示“请先配置沙盒”，Python 解释器开关保持关闭。

这项提示在个人版和完整版都适用：它反映的是当前实例能否安全连接到沙盒，而不是用户是否拥有管理员权限。不要试图通过强制打开解释器绕过它。

### 三种运行方式

| 方式 | 适用 | 配置要点 |
| --- | --- | --- |
| 完整版内置 sidecar | 标准完整版 | Compose 已在内部网络连接 `http://sandbox:8000`，无需暴露端口 |
| 个人版本机 profile | 可信单机 | 设置 `SANDBOX_BASE_URL=http://sandbox:8000` 和匹配密钥，再使用 `--profile sandbox` 启动 |
| 外部沙盒 | 需要隔离或已有执行平台 | 在工具页或启动环境填写 HTTPS 地址和相同 Bearer Key |

无论哪一种，沙盒 API 都不应无鉴权暴露到公网。沙盒密钥是 Bearer 凭据，泄露后可能被用于创建或访问执行会话。

## 本机 sidecar 的安全边界

官方 sidecar 通过宿主机 Docker socket 为每个会话创建受限容器。它尽量限制会话容器的 CPU、内存、进程数、只读根文件系统、临时可写目录、上传大小、空闲回收和执行时长，但 Docker socket 本身仍近似宿主机高权限。

因此：

- 只在完全受控的服务器启用本机 sidecar，不要将它放到不受信任共享宿主机。
- 不给 `sandbox` 添加 `ports`，不通过反向代理暴露它。
- 保留 `SANDBOX_READ_ONLY_ROOTFS=1`，除非你完全理解关闭后的磁盘和写入风险。
- 用 `SANDBOX_MEMORY`、`SANDBOX_CPUS`、`SANDBOX_MAX_SESSIONS`、`SANDBOX_WORKSPACE_SIZE` 和执行时长上限给宿主机保留余量。
- 公开产品默认限制哪些用户、哪些模型可以调用 Python；不要因为容器存在就视为无限可信的任意代码平台。

完整版和个人版可选 profile 都会启动镜像保活服务。它持有沙盒运行时镜像，避免运维脚本清理无引用镜像后，下一次 Python 调用需要冷拉取大镜像并因超时失败。不要把该服务当作多余容器随意删除。

## 持久工作区与文件

沙盒会话通常按对话维度维护工作区，空闲后可回收。配置本地归档或兼容对象存储后，工作区可在会话回收后恢复；本地归档适合单节点，多个应用副本应使用共享对象存储。

持久工作区不等于永久保留所有输出。管理员仍应制定文件保留、备份、删除和用户数据导出策略，并明确对话删除、工作区删除和备份保留之间的关系。包含机密或个人数据的文件不应被自动同步到不受控的对象存储。

## 运行与故障检查

Python 不可用时，依次检查：

1. 工具页是否显示沙盒已配置，地址和密钥是否匹配。
2. 完整版或本机 profile 的 `sandbox` 容器是否运行、是否健康。
3. 宿主机 Docker daemon 与 Docker socket 是否可用，运行时镜像是否已拉取。
4. 沙盒资源上限、并发会话上限、上传大小或执行超时是否过低。
5. 目标模型是否被全局禁用工具、模型策略或工作区权限限制。

不要通过公开沙盒端口、关闭鉴权或无限增大资源限制来解决错误。先读取脱敏后的应用与沙盒日志，确定是网络、鉴权、镜像、资源还是模型授权问题。
