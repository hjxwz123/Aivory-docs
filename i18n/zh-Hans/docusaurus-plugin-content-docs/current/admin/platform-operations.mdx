# 系统、备份与运营

系统设置决定实例如何发送邮件、保存对象、记录日志、展示法律信息和执行备份；运营页面帮助管理员观察用户、模型、文件、资源和反馈。把它们作为持续运维工作，而不是只在第一次安装时填写一次。

## SMTP 与邮件

在“系统 → 邮件服务”填写 SMTP 主机、端口、用户名、密码、发件地址和 TLS 策略。邮件通常用于账号验证、密码重置和运营通知，因此在面向真实用户的完整部署中应尽早配置。

配置时：

- 使用服务商提供的 SMTP 凭据或应用专用密码，不复用管理员密码。
- 发件地址应属于受控域名，并配置必要的 SPF、DKIM、DMARC 或服务商验证。
- 区分直接 TLS 与 STARTTLS 所需端口，按服务商要求填写。
- 保存后用非管理员测试邮箱验证发送、收取、验证码有效期和重置密码流程。

SMTP 未配置时，依赖邮件的功能可能无法完成。不要通过在公开日志中打印验证码或 SMTP 密码来排查问题。

## 存储、上传和保留

“存储与上传”配置应用对象、上传限制和对象存储集成。单节点可以使用本地存储；需要多副本、跨节点访问或外部解析时，应使用受控对象存储。

制定上传与保留策略前先确定：最大单文件、允许类型、用户总空间、预览和产物保存多久、删除后是否有恢复窗口，以及备份是否覆盖对象。提高限制必须同时检查反向代理请求体限制、应用内限制、解析服务容量、磁盘和备份成本。

对象存储凭据与 bucket 配置属于敏感信息。使用单独的最小权限账号，不要授予整个云账号管理员权限；在更换 endpoint、bucket、区域或密钥后，测试上传、下载、预览、解析、分享和删除。

## 法律、联系信息、日志与隐私

在系统设置中维护服务条款、隐私政策、联系入口以及日志/隐私策略。公开服务应提供真实、可处理的联系信息和与实际数据流一致的隐私说明。

日志策略的目标是让管理员能诊断问题，而不是保存更多敏感信息。原则包括：

- 不记录模型服务商 API Key、OAuth Client Secret、支付签名、JWT、刷新令牌、完整用户文件或完整私密提示词。
- 排查时优先使用时间、请求 ID、脱敏错误码、服务名称和聚合指标。
- 设置合理留存和访问权限；日志导出也可能包含用户元数据。
- 对数据导出、删除、备份恢复和第三方服务传输建立负责人和审批流程。

## 公告与内容运营

公告适合维护通知、功能提示和服务状态说明。发布前使用测试账号检查展示范围、关闭行为、移动端排版和链接；紧急公告应简明，避免嵌入敏感内部信息或无法验证的外部脚本。

提示词、技能、图片风格和语音配置会直接影响用户体验和成本。任何面向全体用户的改动先在小范围账号中验证，再逐步开放，并保留可以快速禁用或回退的路径。

## 备份、迁移与配置导出

“备份与迁移”可生成数据迁移归档，也可以导出管理员配置。二者的风险和用途不同：

| 类型 | 通常包含 | 主要用途 | 安全级别 |
| --- | --- | --- | --- |
| 完整数据备份 | 业务数据、向量以及选择的文件/产物 | 灾难恢复、迁移、测试恢复 | 高敏感 |
| 管理员配置导出 | 设置、渠道、模型、身份源、用户组、支付/存储/邮件等配置 | 复制受控环境、变更留档 | 高敏感，常含凭据 |

备份不是创建成功就结束。至少定期在隔离环境验证一次恢复，并检查管理员登录、普通对话、附件、知识库、向量、OAuth、邮件和需要的工具。恢复前停止写入、保留原始数据副本、记录版本和范围；不要把 `docker compose down -v` 用作普通重启命令，它会删除命名卷。

个人版应整体备份 `DATA_DIR`。完整版还必须同时保护数据库、Redis、Qdrant、沙盒归档卷与 `DATA_DIR`。详细命令和恢复顺序见[升级、备份与恢复](../deployment/upgrade-backup.mdx)。

## 用量、分析、资源与反馈

“分析”帮助观察活跃用户、请求和成本趋势；“用量记录”用于查看模型调用与计量；“内容资源”“文件”“反馈”帮助管理文档、图片、工作区资源、上传对象和用户问题。

建议建立定期运营节奏：

1. 每日或每周检查错误率、模型失败、支付异常和高成本用户/模型。
2. 审阅增长趋势、存储占用、知识库任务积压和异常大文件。
3. 将用户反馈关联到实际会话、模型、渠道或功能配置，但避免把私密内容复制到公开工单。
4. 清理测试文件、废弃模板和过期兑换码前确认备份与保留规则。
5. 对向量重建、批量删除、导入/导出等长任务观察进度和结果，再发起下一轮操作。

运营页面提供观察与管理能力，不替代主机级监控。生产实例仍应监控磁盘、内存、容器重启、网络出站、备份成功与证书过期；发现趋势异常时先限制风险能力或用户范围，再做根因排查。
