# Administrator first-run setup

The first account created automatically becomes the administrator. When you open `/admin`, the system shows a guided tour that you can skip and revisit later; it splits configuration into "make it work" and "make it better". Even if you skip the tour, you can reopen it from the admin overview.

The Personal edition and the Full edition share the same administrator configuration model. The difference is that the Personal edition has no local Python sandbox by default, while the Full edition ships with an internal sandbox, PostgreSQL, Redis, and Qdrant by default; they are not two different sets of admin features.

## Make it work: just three steps

Once you complete these three steps, normal chatting can begin. Don't mistake task models, web search, embeddings, email, or Python for hard prerequisites for the first chat.

| Order | Admin location | Completion criteria | Common mistakes |
| --- | --- | --- | --- |
| 1 | AI & models → Channels | At least one channel is enabled and its address, API format, and API Key are usable | Base URL doesn't match the provider's format, or a Key without permission is used |
| 2 | AI & models → Models | At least one enabled chat model is linked to that channel and its model request ID is non-empty | Only embedding/image/audio models were added, or the channel is disabled |
| 3 | AI & models → Model policies | A still-usable default chat model is selected | A model that has been deleted, disabled, or invalidated is selected |

Right after completing them, start a new short conversation to verify the real upstream response. If you receive a channel error, a quota error, or a model-not-found error, fix the channel or model first, then continue configuring other capabilities.

## Step 1: Create a working channel

In "Channels", create one connection per model provider. The channel name is only for administrator identification; what actually affects requests is the API format, Base URL, API Key, and enabled state.

- Select the API format that matches the provider; don't guess the format from the model name alone.
- OpenAI-compatible services usually require a Base URL that includes `/v1`, but the exact path still depends on the provider's documentation.
- The API Key is a server-side secret, persisted only in the admin backend; never put it in browser environment variables, public frontend configuration, screenshots, or logs.
- Ideally, one channel represents one upstream credential that can be rotated and disabled independently. When you need to distinguish regions, accounts, quotas, or gateways, creating multiple channels makes troubleshooting easier.

Only after the channel is saved and enabled should you go to the models page. A channel by itself does not automatically make all of its models appear in the user picker.

## Step 2: Add chat models

A model is a record of a specific callable capability under a channel. When adding a model, at minimum confirm: it is a chat type, it is linked to the correct channel, its request ID exactly matches the provider's actual model ID, and its status is enabled.

Channels that support the model-list endpoint can use "Auto-add models supported by the channel" to import. An import failure doesn't necessarily mean the channel can't chat; common reasons are that the provider doesn't open model-list permission, the gateway doesn't implement the endpoint, or the Key only allows inference. In that case, you can add model IDs manually.

Different channels can reuse the same model ID. For example, if channel A and channel B both have `gpt-5`, you can create two `gpt-5` model records; they are distinguished by their channel associations and can each have their own sort order, labels, quota, and enabled state.

## Step 3: Configure model policies

In "Model policies", select the default chat model. It is the default choice for new conversations and the target checked when the system verifies the minimum working state.

Add the remaining policies according to actual needs:

- Task model: used for some background or auxiliary tasks. It is a health recommendation, not a requirement for ordinary chat.
- Tool-routing model: in automatic tool mode, helps decide whether a tool call is needed; if not configured, the main model's regular policy applies.
- Verification model: used for answer verification or auditing; turning it off never blocks chatting.
- Fallback model and first-token wait threshold: the degradation strategy when upstream is slow, times out, or is unavailable. Use a verified, cost-controllable model.

Run one real conversation after every policy change. Don't rely solely on a model appearing in the dropdown, because channel credentials, provider balance, and model authorization may change afterward.

## Make it better: enable capabilities by use case

After the three steps, extend in the priority order below rather than flipping every switch on day one.

| Capability | Configure first | When you need it | Personal vs. Full edition |
| --- | --- | --- | --- |
| Knowledge bases and RAG | Embedding model, correct dimension, document parsing strategy | Answers must be grounded in private documents | Personal edition uses SQLite embedded vectors; Full edition uses Qdrant |
| Web search | Search provider and API Key/address | Real-time internet information is needed | Configuration is the same |
| Python and file execution | Reachable sandbox, resource limits, model tool authorization | Computation, charts, or file generation are needed | Personal edition has no local sandbox by default; Full edition has one built in |
| MCP, skills, prompts | Start with a single low-risk service or skill | External business systems must be connected | Configuration is the same |
| Email | SMTP, sender address, and TLS | Email verification, password resets, operational notifications | Recommended to prioritize for long-term multi-user Full deployments |
| OAuth and registration policy | Verify the HTTPS domain and a single identity provider first | Third-party login or an organizational entry point is needed | Configuration is the same |
| Workspaces, plans, and payments | Permissions, quotas, credits, and payment callbacks | Serving teams or commercial users | Configuration is the same; full deployments suit long-term operation |

For the security boundaries of RAG, tools, and the sandbox, see [Knowledge bases, RAG, and storage](./knowledge-rag.mdx) and [Tools, MCP, and sandbox](./tools-sandbox.mdx).

## Configuration precedence and change management

Connections and system settings in the admin backend are persisted. Environment variables mainly carry startup defaults, deployment topology, and limits that ordinary administrators cannot change directly; the two are not one set of forms to be filled interchangeably.

- Channel API Keys, payment credentials, SMTP, OAuth, object storage, web search, and most feature switches should be configured in the admin backend and restricted to administrators.
- The official Docker Compose has explicit high-priority values for database, Redis, Qdrant, and built-in sandbox connections; adding a variable with the same name in `.env` won't necessarily override it.
- After environment variable changes, the application or sandbox usually needs a restart; settings saved on admin pages take effect immediately or on the next request, as each page indicates.
- Exporting admin configuration includes sensitive credentials for channels, OAuth, SMTP, storage, and web search. Store admin configuration export files as vault-level secrets.

Before taking on real users, it is recommended to build a "post-change acceptance" checklist: administrator and regular-user login, a chat with the default model, a small file upload, knowledge base retrieval, one restricted tool call, a backup export, and—when needed—an OAuth callback and a payment test.
